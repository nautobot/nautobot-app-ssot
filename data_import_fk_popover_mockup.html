FK Strategy Popover — Design Mockup

The inline popover that appears when a user clicks the strategy cell next to a foreign-key field in the wizard mapping table. This is the most complex micro-interaction in the system — it has to handle four distinct strategies, optional parent-object cascades, and live preview, without overwhelming non-coders.

What's happening in this view

  • Anchored popover, not a modal. The user can still see the mapping table behind it.
  • 4 strategies surfaced upfront — radio cards with a name, a one-sentence explanation, and a badge hinting at safety/use case.
  • Smart default selection: for a required FK with a `name` lookup field, "Lookup · skip record if missing" is preselected. For optional FKs, "Lookup · skip just this field" would be the default.
  • Advanced options collapsed behind a `details` element. Power users can override the lookup field or case sensitivity.
  • Live preview pane shows what would happen for the first 3 records in the cached sample, using the currently selected strategy. Updates in real-time as the user changes choices.
  • "View affected records" link expands a list of all records that would be skipped — surfacing data hygiene issues before the user runs the sync.
  • Anchor hint in the footer reinforces which row this popover belongs to.

Why this scenario matters

Optional FKs need their own default. The recommended badge moves to "skip just this field" so the user is nudged toward the right choice without having to think about it.

Recommendation logic (per FK)

  • Required + has clean source values: Lookup · skip record
  • Required + dirty source data: Lookup or create
  • Optional FK: Lookup · skip just this field
  • Status / role: Lookup or create (commonly missing from source)
  • Manufacturer / DeviceType: Lookup or create with parent cascade

The recommendation system is heuristic — the user always has the final say.

Key idea

When the user chooses "Lookup or create", the popover expands to show a defaults form tailored to the target model. The system has used `SchemaIntrospector` to figure out which fields exist on `extras.Role` — only the ones the user might want to control are shown.

Required fields on the target are pre-filled with sensible defaults the user can edit. The source value automatically fills the lookup field — the user doesn't have to repeat themselves.

Why this is the hard case

Many Nautobot models have required FKs of their own. Auto-creating one means committing to a chain of creates. The system can't make this decision for the user — they have to confirm what the cascade looks like.

The popover handles this by recursively expanding: when the user says "create DeviceType", and DeviceType has a required Manufacturer FK, a nested parent block appears. The user can recurse as deep as needed (limited to 3 levels in practice — deeper than that is a smell).

Visual cascade preview

The resolver chain at the bottom visualizes the auto-creation order. This builds the user's mental model of what the engine will do.

Termination

The cascade terminates when the next-level target has no further required FKs. The popover shows this explicitly: "✓ Manufacturer has no further required FKs. Cascade ends here."

Why "static" matters

Many real-world API responses are missing fields Nautobot considers mandatory. Without a static-value strategy, the user is forced into ugly workarounds (fake JMESPath that always returns the same thing). Making it a first-class strategy keeps the document declarative.

Constrained picker

The dropdown only shows Statuses that are valid for the target model. Nautobot Statuses are filtered by ContentType — we use that filter automatically. Same applies to Roles (which are also content-type constrained).

At-a-glance reference

A summary of every choice the popover surfaces, the document output, and when to recommend each one.

🔍 Lookup · skip record

Look up by attribute. If not found, skip the entire source record (no Device created).

Recommend when: required FK + source data is trusted + missing FK means the record is bad data.

on_missing: skip_record lookup_field: name

🔍 Lookup · skip field

Look up by attribute. If not found, leave just this field blank. Record still gets created.

Recommend when: optional FK + you'd rather have the record without this relationship than skip it.

on_missing: skip_field lookup_field: name

✨ Lookup or create

Look up. If not found, create with defaults. Recursively handles parent FKs via also_emit.

Recommend when: the FK target represents a growing catalog (Role, DeviceType, Manufacturer).

on_missing: create create_defaults: { ... } also_emit: { parent chain... }

📌 Static value

Ignore the source. Always use one fixed Nautobot object. Picker constrained to valid choices.

Recommend when: source has no usable data for this FK + every record should land at the same place.

on_missing: static static_value: "Active"

Design principles

  • Anchored, not modal — keep the mapping table in view so context is never lost.
  • Smart defaults — preselect the strategy that's right for the field type (required vs optional, content-type-constrained vs free, etc.). The user overrides only when necessary.
  • Progressive disclosure — collapse advanced options. Show the parent cascade only when the user chooses `create`.
  • Live preview — show what would happen for the first few cached sample records using the current settings. Updates in real time.
  • Affected-record drilldown — surface which records would be skipped or created before the user runs the sync.
  • Constrained pickers — for Status/Role/etc., filter the choices by ContentType automatically.
  • Cascade visualization — when parent objects auto-create, show the chain explicitly so users build the right mental model.
  • YAML mirrors UI — every choice in the popover writes to exactly one path in the document. Reversible: opening a popover on a configured field shows its current state.
